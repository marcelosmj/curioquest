A descoberta que define o plano

A primeira leitura sugeria um desastre: 267 das 309 classes de interface declaram campos públicos de display (public var closeBtn:SimpleButton). Isso é vínculo com símbolos autorados no Flash IDE — essas classes não são código autossuficiente, são code-behind de peças visuais. Se o layout tivesse de ser remontado à mão, seriam 267 telas redesenhadas e o port deixaria de fazer sentido.

Mas o layout não se perdeu: ele está dentro do próprio Pets.swf. A tabela SymbolClass do arquivo lista 274 símbolos com vínculo de classe, 271 deles ui.* — cada tela é um símbolo ligado à sua classe. E o SWF é convencional: 549 DefineSprite, 624 DefineEditText, 284 DefineShape, apenas 2 fontes embutidas, nada de Stage3D ou vídeo.

Consequência

O OpenFL consome SWF como biblioteca de assets, com vínculo de símbolo a classe. Portanto a interface não precisa ser redesenhada: os 1.687 campos de símbolo são declaração, e o trabalho real é traduzir as 2.701 funções de comportamento. É a diferença entre um port caro e uma reescrita inviável.

O runtime AIR embutido — 24,6 MB de .so e .jar, só armeabi-v7a — sai do pacote. É ele que hoje impede um build 64 bits e que envelhece a cada versão do Android.

A rede encolhe de 96 mensagens para uma

O protocolo parece assustador e não é. Das 96 mensagens ElectroServer mapeadas, o jogo usa nove: login, conexão, plugin, sala e zona. E toda a lógica viaja dentro de um único envelope de plugin, endereçada por DALC_ID + ACTION_TYPE.

As 45 ações são o contrato real e não mudam. Muda só como são embrulhadas — e é por isso que 55 mil linhas de SDK e Thrift podem ser apagadas sem perder funcionalidade.

Ordem de execução

F1

Provar a hipótese antes de investir

dias, não semanasdecide todo o resto

Extrair o Pets.swf como biblioteca OpenFL e subir uma tela — a mais acoplada que houver, o MenuScreen com seus 32 campos de símbolo. Se os campos forem preenchidos a partir do símbolo, o plano inteiro se sustenta. Se não forem, pare aqui: sem isso o port vira redesenho de 267 telas e a conta muda.

F2

Transporte novo, servidor igual

~6.300 linhasservidor ganha um adaptador

Trocar ElectroServer+Thrift por JSON sobre WebSocket, mantendo as 45 ações e os nomes de campo. O servidor Python passa a falar os dois dialetos no mesmo processo, de modo que o cliente AIR atual continue funcionando enquanto o novo nasce — sem big bang.

F3

Modelo de domínio

27.834 linhastradução quase mecânica

model/ é lógica pura: leitores de livro, fórmulas de atributo, dados de curio. AS3 e Haxe são próximos o bastante para isso ser conversão direta, e há um oráculo para conferir cada fórmula — o servidor Python já as reimplementa e concorda com o cliente.

F4

Telas, por ordem de uso

2.701 funçõeso grosso do trabalho

Seguir o caminho do jogador: login → menu → zona → batalha → curio → loja. As pesadas são conhecidas: MenuScreen (2.503 linhas), RevampedPetWindow (1.148), BattleScreen (1.104) e BattlePlugin (1.091). As telas de PvP, clubes e eventos podem ficar por último — o servidor ainda não as atende.

F5

Empacotar 64 bits e aposentar o AIR

−24,6 MBfim da data de validade

Build Android nativo pelo OpenFL, sem runtime embutido e sem as duas ANEs (analytics e compra, ambas descartáveis offline). Aposentar o cliente AIR só quando o novo empatar em funcionalidade.

O que o port não conserta

Nenhuma tecnologia devolve conteúdo perdido. Os 129 curios sem arte continuam sem arte, e as zonas além da segunda continuam sem cenário. O port resolve longevidade e manutenção — não acervo.

Recomendação

Fazer a F1 antes de qualquer decisão. Ela custa dias e responde a única pergunta que pode inviabilizar tudo. Enquanto ela não for respondida, qualquer estimativa de prazo para o port é chute — inclusive as deste documento.

Enquanto isso, continuar investindo no servidor e no conteúdo, que sobrevivem intactos a qualquer decisão de cliente: são 4.638 linhas e 46 livros que valem igual no AIR de hoje e no Haxe de amanhã.

E manter em vista que o gargalo atual não é o port: é o travamento do ENTER_BATTLE no aparelho, que precisa do JPEXS para ser instrumentado. Um port dissolve esse problema — num cliente seu, basta um trace — mas leva meses, e o travamento pode levar horas se a ferramenta estiver à mão.
